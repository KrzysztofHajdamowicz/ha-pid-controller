# Contribution guidelines

Contributing to this project should be as easy and transparent as possible, whether it's:

- Reporting a bug
- Discussing the current state of the code
- Submitting a fix
- Proposing new features

## Development environment

The project uses [uv](https://docs.astral.sh/uv/) to manage Python and the dependencies. Home Assistant is installed as a development dependency, so its source code is available in `.venv` for reference.

```bash
./scripts/setup          # creates .venv, installs dependencies and git hooks
uv run pytest            # runs the tests
./scripts/lint           # formats and lints the code with ruff
./scripts/develop        # starts a development Home Assistant on http://localhost:8123
```

The git hooks (run by [prek](https://prek.j178.dev/), a drop-in replacement for pre-commit) format the code, keep `uv.lock` up to date and type check it with mypy.

A [devcontainer](.devcontainer.json) with everything preinstalled is available for Visual Studio Code.

`scripts/smoke_test.py` boots a real Home Assistant instance with the integration and works with any installed release, including betas: `uv run python -I scripts/smoke_test.py`. CI runs it against the current, the minimum supported and the latest pre-release of Home Assistant.

Entity snapshots live in `tests/snapshots/`; after an intended change of the entities run `uv run pytest tests/test_entities.py --snapshot-update` and review the diff.

## Pull requests

1. Fork the repo and create your branch from `dev`.
2. Follow the current [Home Assistant developer documentation](https://developers.home-assistant.io/) for integrations.
3. Add or update tests for your change and make sure `uv run pytest` passes (coverage must stay at 95 % or more).
4. Make sure `./scripts/lint` and `uv run mypy` report no issues.
5. If you've changed behaviour, update the documentation.
6. Open the pull request against `dev`.

Every change goes through a pull request. The release notes are generated from the pull requests, grouped by label, so give each one a label: `breaking`, `enhancement`, `bug`, `documentation`, `tests` or `dependencies` (`skip-changelog` leaves it out of the notes). The categories are configured in [.github/release.yml](.github/release.yml).

## Releasing

Releases are made by the [Release workflow](.github/workflows/release.yml): open Actions → Release → Run workflow on the `dev` branch and enter the version, e.g. `v2.1.0`. A suffix (`v2.1.0-beta1`, also `-pre`, `-alpha`, `-rc`) publishes a pre-release. Tick "Dry run" to preview the release notes in the job summary without publishing anything.

The workflow requires a green CI run on the current commit, commits the version to `manifest.json`, tags it, attaches `pid_controller.zip` and publishes the release with notes generated by GitHub since the previous release (the previous stable release for a stable version).

## Report bugs using GitHub's [issues](../../issues)

GitHub issues are used to track public bugs. Report a bug by [opening a new issue](../../issues/new/choose).

**Great bug reports** tend to have:

- A quick summary and/or background
- Steps to reproduce (be specific, give sample configuration if you can)
- What you expected would happen
- What actually happens
- Debug logs (`logger: logs: custom_components.pid_controller: debug`) and the diagnostics download of the integration entry
